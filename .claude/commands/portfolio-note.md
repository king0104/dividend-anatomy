# /portfolio-note — 기술 포트폴리오 문서 작성

목적: 포트폴리오에 쓸 글은 결과물 나열이 아니라 "무엇이 문제였고, 왜 그
조치를 택했고, 실제로 뭐가 바뀌었는지"가 숫자로 드러나야 한다. 대화
중 실제로 겪은 일을 나중에 기억에 의존해 재구성하면 트레이드오프와
실측값이 흐려진다 — 작업이 끝난 시점에 바로 기록한다.

대상 작업: $ARGUMENTS

## 지켜야 할 것

- 지금까지의 대화에서 실제로 완료된 기술 작업 하나를 특정한다. 여러
  개가 섞여 있으면 어떤 걸 기록할지 사용자에게 먼저 확인한다.
  `$ARGUMENTS`가 비어 있으면 대화 맥락에서 가장 최근에 마무리된 작업을
  찾아 이거 맞는지 확인한다.
- `docs/portfolio/` 안의 기존 파일과 번호가 안 겹치게
  `{다음번호}-{짧은-영문-slug}.md` 파일을 새로 만든다.
- 아래 구조를 따르되, **각 섹션은 실제로 있었던 일만** 쓴다 — 대화에
  없던 수치나 과정을 그럴듯하게 채우지 않는다. 빠진 정보는 사용자에게
  묻는다.
  1. **제목** — 무엇을 해결했는지 한 줄 (기술 키워드 포함, 예: "N+1
     쿼리 제거", "인증 캐시 무효화 버그 수정").
  2. **날짜**, **관련 커밋**(해시), 관련 결정 문서(`docs/decisions/`)가
     있으면 링크.
  3. **문제** — 무엇이 문제였는지, 어떻게 발견했는지(코드 리뷰 중 감지,
     장애로 드러남, 실측 중 발견 등). "느릴 것 같다"는 감과 "실제로
     확인된 사실"을 구분해서 쓴다.
  4. **조치** — 검토한 대안과 그중 하나를 고른 이유(트레이드오프
     포함). 코드 스니펫은 핵심 diff 3~5줄만, 나머지는 파일:줄 참조로
     대체한다.
  5. **결과** — 반드시 수치나 재현 가능한 관찰로 뒷받침한다(쿼리
     수, 응답 시간, 에러율 등 실측값). "빨라졌다" 같은 정성적 표현만
     쓰지 않는다 — 실측이 없으면 이 섹션을 비워두고 사용자에게
     측정 방법을 먼저 제안한다.
  6. **다음/한계** — 일부러 범위를 좁힌 부분, 남은 위험, 후속 과제.
- 어조는 기술 면접관이 읽는다고 가정하고 담백하게 — 과장·마케팅
  문구·이모지 없이, "왜"가 최소 2번(선택 이유 + 설계/검증 이유)
  드러나게 쓴다.
- 문서 작성 후, 이미 발행된 Artifact나 스크린샷 등 시각 자료가 있으면
  그 링크를 문서 안에 남긴다(중복 재작성하지 않는다).
- 작성 후 별도 커밋으로 남긴다(다른 코드 변경과 섞지 않는다). 커밋
  메시지에 이 문서가 다루는 작업을 한 줄로 요약한다.
- 커밋 후, 이 내용을 Artifact(시각 자료)로도 만들지, 아니면 이 markdown
  문서 자체로 충분한지 사용자에게 물어본다 — 매번 자동으로 Artifact를
  만들지 않는다.
