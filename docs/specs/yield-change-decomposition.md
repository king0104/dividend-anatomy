# 배당수익률 변화 기여도 분해 (Yield Change Decomposition)

이 프로젝트의 핵심 기능. "배당수익률이 올랐다"는 사실 하나를 가격 하락
때문인지, 배당 자체가 늘어서인지 두 숫자로 쪼갠다.

## 0. 스코프

- 이 지표는 **종목 자체의 배당수익률 변화**를 설명한다. "내가 특정일에
  샀으면 배당을 받았는가"(T+1 보유 판정, [[02-ex-dividend-t1-rule]])는 이
  지표의 관심사가 아니다 — TTM 배당 합계는 이미 확정된 과거 지급 이력의
  합이므로 보유 여부 판정이 개입하지 않는다.
- 배당/주가가 모두 원래 통화(예: USD) 기준 비율이므로 **환율 변환이
  필요 없다.** CLAUDE.md의 "환율은 배당 지급일 기준" 원칙은 이 지표가
  아니라 "원화 환산 실수령액" 같은 별도 지표에 적용된다.
- TTM 배당 합계에는 **정기 배당만** 포함한다. 정기/특별배당 분리 로직
  자체(지급 이력에서 주기를 추론하는 알고리즘)는 이 스펙의 범위가 아니고,
  이미 분류된 "정기 배당 목록"과 "종목별 연간 지급 횟수(N)"를 입력으로
  받는다고 전제한다. (그 분류 로직 자체 스펙은 필요 시
  `docs/specs/regular-dividend-classification.md`로 분리 — 아직 미작성.)

## 1. 계산식

### 1.1 입력 변수

| 변수 | 정의 |
|---|---|
| `t1` | 비교 종료 시점 (기준일, 아래 "기준 시점" 참고) |
| `t0` | 비교 시작 시점 = `t1`의 정확히 1년 전 |
| `P(t)` | `t` 시점 "가장 가까운" 종가 (BigDecimal, 이미 확정된 프로젝트 원칙 — 정확히 이 날짜가 아니라 이전·근처 최근접값) |
| `N` | 해당 종목의 연간 정기 배당 지급 횟수 (분기=4, 월배당=12, 반기=2, 연 1회=1 — 입력으로 주어짐) |
| `D_actual(t)` | `t` 기준 trailing 12개월 창 안에서 **실제로 발견된** 정기 배당 지급액의 합 |
| `k(t)` | `t` 기준 창 안에서 발견된 정기 배당 지급 **횟수** (0 ≤ k ≤ N) |
| `D_annualized(t)` | `k(t) > 0`이면 `D_actual(t) * N / k(t)`, `k(t) = 0`이면 계산 불가(undefined) |

### 1.2 TTM 배당 합계 — 실제합산과 연환산 둘 다 계산

```
window = (t - 12개월, t]  (시작점 제외, 끝만 포함 — docs/decisions/05-ttm-window-boundary-fix.md)
found = window 안의 정기 배당 지급 목록 (특별배당 제외, 이미 분류된 것으로 간주)
k(t) = found.size()
D_actual(t) = sum(found.amount)   // BigDecimal 합, 반올림 없이 그대로
D_annualized(t) = k(t) > 0 ? D_actual(t) * N / k(t) : null
completeness(t) = k(t) / N        // 1.0이면 완전, 그 미만이면 구멍 있음
```

`k(t) == 0`인 경우 `D_annualized`는 계산하지 않는다 (0으로 나눌 수 없고,
"연환산"이라는 개념 자체가 성립하지 않음 — 아래 예외 케이스 참고).

### 1.3 배당수익률

```
Y_actual(t)     = D_actual(t) / P(t)
Y_annualized(t) = D_annualized(t) / P(t)     // D_annualized(t)가 있을 때만
```

### 1.4 기여도 분해 (대칭/평균법)

`t0`, `t1` 두 시점의 배당(`D`)·가격(`P`) 각각의 변화가 수익률 변화에
얼마나 기여했는지를, "가격만 먼저 바뀌었다고 가정" / "배당만 먼저 바뀌었다고
가정" 두 순서를 평균 내어 계산한다. 어느 쪽을 먼저 바꿨다고 가정하느냐에
따라 결과가 달라지는(order-dependent) 순차 분해 대신 이 방식을 쓰는 이유는
정당한 임의성(어느 쪽이 "먼저"인지 정할 근거가 없음)을 없애기 위해서다.

```
ΔY = Y(t1) - Y(t0) = D1/P1 - D0/P0

가격 기여도(price_contribution)
  = ½[(D0/P1 - D0/P0) + (D1/P1 - D1/P0)]
  = (D0 + D1) / 2 * (1/P1 - 1/P0)          ← 구현에 쓸 닫힌 형태

배당 기여도(dividend_contribution)
  = ½[(D1/P0 - D0/P0) + (D1/P1 - D0/P1)]
  = (D1 - D0) / 2 * (1/P0 + 1/P1)          ← 구현에 쓸 닫힌 형태

항등식(반드시 성립, 테스트로 고정): price_contribution + dividend_contribution == ΔY
```

이 분해를 `D_actual`, `D_annualized` 두 계열에 대해 **각각 독립적으로**
수행해 두 벌의 결과를 만든다 (아래 "구멍 처리" 참고). 즉 최종 출력은:

- `실제합산 기준`: `price_contribution_actual`, `dividend_contribution_actual`
- `연환산 기준`: `price_contribution_annualized`, `dividend_contribution_annualized` (둘 중 하나라도 `D_annualized`가 undefined면 이쪽 전체를 생략하고 "연환산 불가" 표시)

### 1.5 BigDecimal 연산 규칙

- 나눗셈은 전부 `MathContext.DECIMAL64` (유효숫자 16자리)로 수행한다 —
  scale을 안 정하고 나누면 순환소수에서 `ArithmeticException`이 난다.
- 반올림은 **최종 %p 출력 직전에만** 한 번 적용한다 (아래 "반올림 방향"
  참고). 중간 계산(위 1.2~1.4)에서는 반올림하지 않는다.

## 2. 기준 시점

- `t1` = 조회 요청 시점의 "최근 확보된 거래일" (해당 종목의 가격 시계열
  중 가장 최신 날짜).
- `t0` = `t1`의 **정확히 1년 전 같은 날짜**(`t1.minusYears(1)`), 그 날짜의
  가격은 "가장 가까운 값" 조회 원칙을 그대로 적용한다 (주말/휴장일이면
  직전 근접 거래일).
- 월별 차트(Day 10-12)에서는 매월 말일을 `t1`로 삼아 이 계산을 반복해서
  라인으로 이어 보여준다 — 즉 이 스펙은 "임의의 한 시점 t1에 대한 계산"
  하나이고, 월별 차트는 이걸 여러 `t1`에 대해 반복 호출한 결과다.
- TTM 배당 창(`window`)의 기준일도 각각 `t0`, `t1` 그 자체다 (예:
  `t1 = 2026-08-22`이면 window는 `2025-08-22 ~ 2026-08-22`).

## 3. 반올림 방향

- 중간 계산(BigDecimal 나눗셈, 곱셈, 뺄셈)은 반올림하지 않는다 (1.5 참고).
- 화면/API에 노출하는 최종 `price_contribution`, `dividend_contribution`,
  `Y_actual`, `Y_annualized`는 **%p 단위로 변환(×100) 후 소수 2자리,
  `RoundingMode.HALF_UP`**으로 반올림한다.
- 이유: 회계 장부가 아니라 화면에 보여주는 지표이므로 일반적으로 익숙한
  올림 방향(HALF_UP)이 직관적이고, 배당수익률·퍼센트 지표 관례상 소수
  2자리가 표준적인 정밀도다.
- 반올림 후에도 `price_contribution + dividend_contribution`이 반올림 전
  `ΔY`의 반올림값과 **±0.01%p** 이내로 일치하는지 테스트로 확인한다 (각각
  따로 반올림하면 합이 틀어질 수 있음 — 이 오차는 허용하되 문서화한다).

## 4. 예외 케이스

| 상황 | 처리 |
|---|---|
| `k(t) == 0` (창 안에 정기 배당 지급 이력이 전혀 없음) | `D_actual(t) = 0`으로 계산은 진행하되(배당 미지급 구간일 수 있음), `D_annualized(t)`는 계산하지 않고 이쪽 결과 전체를 생략. 화면에 "이 구간 배당 지급 이력 없음" 표시 |
| `0 < k(t) < N` (구멍 있음, 사용자 결정) | `D_actual`, `D_annualized` **둘 다 계산해서 함께 노출**. `completeness(t) = k(t)/N`도 같이 보여주고, `completeness < 1.0`이면 "데이터 불완전 (n/N 회만 확인됨)" 배지 표시. 조용히 하나만 보여주지 않는다 |
| 종목이 배당을 아예 지급한 적 없음(전체 이력 0건) | `k(t)=0`이 `t0`, `t1` 양쪽 다 해당 — 지표 자체를 "배당 미지급 종목"으로 표시하고 기여도 분해를 시도하지 않음 (0/0 방지) |
| `P(t0)` 또는 `P(t1)` 조회 실패 (시계열 구멍이 너무 커서 근접값도 못 찾음, 예: 상장 1년 미만) | 계산 자체를 생략, "가격 데이터 부족" 표시. 절대 0이나 추정치로 대체하지 않는다 |
| 창 구간 안에 주식분할이 있었던 경우 | Massive가 주는 배당 금액이 분할조정(split-adjusted)인지 raw인지 먼저 확인 필요. 조정 안 된 값이면 분할 이력을 조회해 배당액을 분할비율로 나눠 단위를 맞춘 뒤 합산한다. (CLAUDE.md "분할 전후 단위 불일치" 예측 항목과 직결 — `docs/ai-predictions.md` #4) |
| 창 구간에 특별배당이 섞여 있음 | 이 스펙 진입 전에 이미 정기/특별 분리가 끝났다고 전제 (0절 스코프 참고) — 분리가 안 된 원시 데이터가 들어오면 이 로직의 버그가 아니라 상류 분류 로직의 버그로 처리 |
| `N`(연간 지급 횟수) 추론 자체가 애매한 종목 (예: 배당 이력이 짧아 주기를 특정하기 어려움) | `N` 추론 로직의 책임 — 이 스펙에서는 `N`이 확정되어 들어온다고 가정하고, `N`이 없으면 지표 계산 자체를 보류 |

## 5. CLAUDE.md 정합성 체크

- ✅ 전 과정 `BigDecimal`, `double`/`float` 미사용 (ArchUnit이 강제)
- ✅ 특별배당은 정기 배당과 분리해서 다룸(0절)
- ✅ 데이터 불완전 시 조용히 넘어가지 않고 화면에 표시(4절)
- ✅ 투자 판단/추천 문구 없음 — 이 지표는 "왜 바뀌었는지"만 보여주고
  "그래서 사라/팔아라"는 말하지 않는다
- ✅ 세금 로직 없음 (이 지표는 세전 배당수익률만 다룸 — 세금은 별도
  "실수령액" 지표에서만 마지막 단계에 적용)
