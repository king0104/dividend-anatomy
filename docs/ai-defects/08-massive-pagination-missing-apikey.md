# 08. Massive `next_url` 페이지네이션에 apiKey가 없다는 걸 못 잡고 넘어감

**날짜**: 2026-08-25
**관련 커밋**: (이 문서와 같은 커밋)

## 무슨 일이 있었나

배당킹 유니버스를 5종목에서 57종목으로 확대하면서 51개 종목을 순서대로
수집했다. 대부분은 성공했는데 CBSH(Commerce Bancshares)와
TR(Tootsie Roll Industries) 딱 두 종목만 `401 Unauthorized: "API Key
was not provided"`로 실패했다. Massive에서 발급받은 토큰으로 직접
`curl`을 날려보면 정상 응답이 왔다 — 토큰 자체는 멀쩡했다.

## 왜 놓칠 뻔했나

`MassiveClient.java`의 주석이 이렇게 단정하고 있었다:

> next_url은 Massive가 이미 apiKey 쿼리 파라미터까지 포함해서 내려준다
> (check_massive_api.py에서 확인한 패턴)

이 검증은 Day 1에 KO 하나만 대상으로 했다. KO는 분할 이력이 1건뿐이라
애초에 페이지네이션(`next_url`)이 발생하지 않는 케이스였다 — 즉
"apiKey가 next_url에 포함돼 있다"는 주장이 **한 번도 실제로 실행되지
않은 코드 경로**에 대한 결론이었다. 51개 중 49개 종목도 분할 이력이
10건(Massive 기본 페이지 크기) 미만이라 우연히 같은 사각지대에 있었고,
CBSH(22건)·TR(23건)처럼 오래된 회사라 분할이 많은 종목에서만 실제
페이지네이션이 발생해서 버그가 드러났다.

## 어떻게 잡았나

CBSH의 `/v3/reference/splits`를 직접 `curl`로 호출해서 응답의
`next_url` 필드를 확인했다 — `apiKey` 파라미터 없이
`?cursor=...`만 있었다. 코드 주석의 전제 자체가 틀렸다는 걸 실제 API
응답으로 반증했다.

## 어떻게 고쳤나

`MassiveClient.fetchAllPaginated`에서 `next_url`을 그대로 따라가지
않고, 매번 `apiKey` 쿼리 파라미터를 직접 붙여서 요청하도록 수정.
CBSH(분할 22건)·TR(분할 23건) 둘 다 재수집해서 정상 완료됨을 확인.

## 교훈

- **"한 종목으로 검증했다"는 "모든 경로를 검증했다"가 아니다.**
  페이지네이션처럼 입력 크기에 따라서만 발동하는 코드 경로는, 우연히
  작은 데이터셋으로만 검증하면 몇 달이고 안 드러날 수 있다. 이번에도
  57종목 중 49종목이 같은 사각지대(분할 10건 미만)에 있어서 유니버스를
  대폭 늘리기 전까지 발견되지 않았다.
- **API 문서/코드 주석에 남긴 "확인했다"는 재검증 없이 오래 믿으면
  위험하다.** 이 주석은 Day 1 검증 스크립트 결과를 근거로 몇 주간
  아무 의심 없이 유지됐다.
- 실데이터 검증 규모를 키우는 것 자체가 새로운 버그를 드러내는
  경우다(`docs/ai-defects/07`과 같은 패턴) — 이번엔 종목 수를 5개에서
  57개로 늘리는 과정 자체가 검증 범위 확대 역할을 했다.
