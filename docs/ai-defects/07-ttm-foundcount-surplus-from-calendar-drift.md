# 07. TTM 창 경계 수정(defect 04)이 실제 데이터엔 불충분했음 — 진짜 원인은 캘린더 드리프트

**날짜**: 2026-08-23
**관련 커밋**: (이 문서와 같은 커밋)

## 무슨 일이 있었나

`docs/ai-defects/04-ttm-window-boundary-overlap.md`에서 남겨둔
"실제 데이터에서도 경계 중복이 있을 수 있다"는 위험을 삭감 이력 탐지
지표를 KO 실데이터로 검증하다가 실제로 겪었다(`foundCount(5) >
expectedCount(4)`로 400). 창을 "양 끝 포함"에서 "시작점 제외, 끝만
포함"으로 고쳐서 배포했는데, **다시 KO로 curl 해보니 여전히 400**이
났다.

## 왜 놓칠 뻔했나

첫 수정 직후 전체 테스트(`./gradlew test`, 59개)가 다 통과해서 "고쳤다"고
판단할 뻔했다. 하지만 테스트는 전부 손으로 만든 소수의 날짜 조합이라,
"정확히 12개월 차이 나는 경계 정렬" 케이스 하나만 겨냥했지 실제 22년치
KO 데이터 전체의 불규칙한 지급 간격(77일~102일)까지는 재현하지 못했다.
경계 정의(포함/제외)만 고치면 될 거라고 가정한 게 착각이었다 — 진짜
원인은 "실제 분기 배당이 정확히 91.25일 간격이 아니다"라는, 경계
정의와 무관한 더 근본적인 사실이었다.

## 어떻게 잡았나

수정을 배포하고 실제 서버를 재기동해서 `curl
localhost:8080/api/tickers/KO/dividend-cuts`로 다시 확인하는 습관이
아니었으면 몰랐을 것 — 유닛 테스트만 믿었으면 여기서 멈췄다. 400이
다시 뜨자, KO의 실제 지급일 88건 전체를 뽑아서 파이썬으로 "모든
지급일을 창 끝으로 삼았을 때 몇 건이 잡히는가"를 전수 시뮬레이션했다.
결과: 30개 창에서 `foundCount=5`. 그중 하나(`windowEnd=2005-06-13`)를
직접 까보니 지급 간격이 91일/77일/102일/94일로 불규칙해서, 시작점을
제외해도 4번의 지급이 자연스럽게 366일 안에 다 들어가는 걸 확인했다.

## 어떻게 고쳤나

`docs/decisions/05-ttm-window-boundary-fix.md`의 "추가 발견" 절 참고.
요약: `TtmDividendSummary`가 `foundCount > expectedCount`를 더 이상
막지 않게 하고(`isComplete()`도 `>=`로 재정의), `DividendCutDetector`의
비교 기준을 `actualSum`에서 `annualizedSum`(캘린더 드리프트를
정규화한 값)으로 바꿨다.

## 교훈

- **유닛 테스트 통과 ≠ 실제 데이터로 검증 완료.** 손으로 만든 테스트
  케이스는 "내가 생각한 문제"만 재현한다 — 실제 20년치 데이터가 만드는
  불규칙성은 전수로 훑어봐야 드러난다.
- **첫 진단이 그럴듯해 보여도 재검증한다.** "경계 정렬 문제"라는 첫
  진단은 부분적으로 맞았지만(실제로 그런 케이스도 있었다) 전체 원인은
  아니었다 — 고치고 나서 바로 "됐다"고 하지 않고 실제 서버로 다시
  확인했기 때문에 이 차이를 알아챘다.
- 이런 종류의(전수 데이터 필요한) 검증은 `/verify`의 손계산 대조만으로는
  안 잡힌다 — 실제 데이터 전체를 스크립트로 훑어보는 단계가 별도로
  필요하다는 걸 `docs/workflow.md`에 반영할지 검토할 가치가 있다.
