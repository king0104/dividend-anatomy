# 02. 티커 목록 N+1 제거 — 반복 조회를 배치 조회로

**날짜**: 2026-08-25
**관련 커밋**: `7e046b0`(최종 수정), `4d37069`+`9109372`(첫 시도가 운영에서 응답 44초로
튄 걸 실측하고 되돌린 기록 — 실패도 그대로 남긴다)
**관련 문서**: [01. N+1 쿼리 제거 — 배당 건별 분할 이력 재조회](01-n-plus-one-query-fix.md)의 후속 작업

## 문제

01번 문서에서 고친 건 "배당 지급 건수만큼" 반복되던 쿼리였다. 그런데
`TickerSummaryService.summarizeAll()`([TickerSummaryService.java](../../src/main/java/com/dividendanatomy/service/ticker/TickerSummaryService.java))을
다시 읽다가, 그 수정과는 **다른 층위의 반복**이 남아 있는 걸 발견했다 —
티커 57개를 순회하며 `summarize(symbol)`을 개별 호출하는데, 그 안에서
`tickerRepository.findBySymbol()`(이미 `findAll()`로 가진 Ticker를 재조회),
배당 이력, 분할 이력, 가격을 매 티커마다 따로 조회하고 있었다. 티커당
6개 쿼리 × 57 ≈ 342건 — 01번 수정으로 5,124건이 343건까지 줄긴 했지만,
그 343건 자체가 "배당 건수"에서 "티커 수"로 반복 단위만 바뀐 같은 모양의
N+1이었다.

이걸 고치기 전에 먼저 확인한 게 있다. 01번 문서의 "48초→3.6초"는
Bastion SSH 터널을 거쳐 로컬에서 잰 값이었는데, 사용자가 "실제 체감은
5초 정도였던 것 같다"고 지적했다. 계산해보니 맞았다 — N+1의 총 소요
시간은 대략 **"쿼리 횟수 × 쿼리 1건당 왕복 지연"**인데, 터널 경유는
노트북→인터넷→SSH→OCI 리전이라는 추가 홉 때문에 쿼리당 지연 자체가
인클러스터 경로보다 훨씬 크다(역산하면 터널 약 9.4ms/쿼리, 실측
필요). 실제로 임시 `git revert`로 01번 수정 전 코드를 운영에 재배포해
직접 잰 값은 7.73s / 9.46s / 16.91s(평균 11.36s)였다 — 터널이 잰
48초보다 훨씬 빠르지만, 그래도 느린 건 사실이었다. 그래서 이번엔
처음부터 "실제 운영 응답시간"을 기준으로 삼기로 했다.

## 조치

**배치 조회로 재구성**: `DividendPaymentRepository`/`SplitEventRepository`에
`findByTickerIn...`을 추가해 57번의 개별 조회를 `IN` 절 1번씩으로
합치고, 결과를 `Collectors.groupingBy(ticker.getId())`로 메모리에서
티커별로 나눴다. `TtmDividendAggregationService`는 배당 변동성·삭감
감지·성장 둔화·수익률 분해 4개 화면이 함께 쓰는 공용 컴포넌트라 이번
범위에서 일부러 제외했다 — 배치로 묶으려면 그 4곳의 호출 패턴까지
다시 설계해야 해서, "티커 목록 화면 느림"이라는 원래 범위를 벗어난다.

**첫 시도(실패)**: 가격은 "티커별로 조건에 맞는 최신 1행"이 필요해서
단순 `IN` 조회로 안 됐다. 그래서 상관 서브쿼리를 썼다:

```java
// 실패한 첫 버전 — PriceBarRepository
@Query("""
    SELECT p FROM PriceBar p
    WHERE p.ticker IN :tickers
      AND p.date = (SELECT MAX(p2.date) FROM PriceBar p2
                     WHERE p2.ticker = p.ticker AND p2.date <= :onOrBefore)
    """)
List<PriceBar> findLatestOnOrBeforeForTickers(...);
```

기존 단위 테스트(`@DataJpaTest`, 임베디드 H2)는 다 통과했고, 정확성도
맞았다. 그래서 그대로 커밋(`4d37069`)해 배포했는데, 실제 운영
`GET /api/tickers` 응답이 **41.8초 / 44.1초**로 튀었다 — 수정 전(11초대)보다
훨씬 나빠진 것. 바로 `git revert`(`9109372`)로 되돌리고 원인을 봤다.

**원인**: 이 상관 서브쿼리는 바깥쪽 `price_bar` 행(사실상 테이블
대부분) **하나하나마다** 서브쿼리를 다시 실행한다. MySQL이 이런
행 단위 상관 서브쿼리를 항상 영리하게 최적화해주지 않는다 — 57번의
개별 "top-1" 쿼리보다 오히려 더 비싼 실행 계획이 나온 것으로 보인다.
H2 기반 테스트가 이걸 못 잡은 이유는, 테스트가 **결과값의 정확성**만
확인했지 **실행 계획**은 검증하지 않았기 때문이다 — H2와 MySQL의
쿼리 플래너는 이런 구조를 다르게 처리한다.

**수정(성공)**: "티커별 최신 날짜"를 `GROUP BY`로 먼저 구하고, 그
결과에 `JOIN`하는 방식으로 바꿨다. `GROUP BY`는 `(ticker_id, date)`
유니크 인덱스로 MySQL이 잘 최적화하는 반면, 행 단위 상관 서브쿼리는
그렇지 않다.

```java
// 수정된 버전 — PriceBarRepository (네이티브 쿼리)
@Query(value = """
    SELECT p.* FROM price_bar p
    INNER JOIN (
        SELECT ticker_id, MAX(date) AS max_date FROM price_bar
        WHERE ticker_id IN (:tickerIds) AND date <= :onOrBefore
        GROUP BY ticker_id
    ) latest ON p.ticker_id = latest.ticker_id AND p.date = latest.max_date
    """, nativeQuery = true)
List<PriceBar> findLatestOnOrBeforeForTickerIds(...);
```

**검증**: 이번엔 배포 전에 운영 DB에 `EXPLAIN ANALYZE`로 직접 붙어
확인하려 했으나, SSH+시크릿 조회+임시 파드 생성이 결합된 명령이라
Claude Code의 자동 승인 분류기가 막았다. 대신 구조적으로 안전한
JOIN 방식으로 바로 수정·배포한 뒤, 배포 직후 응답시간을 즉시 확인해
문제가 있으면 바로 되돌릴 수 있게 준비해두고 진행했다. `summarizeAll()`이
개별 `summarize()`와 정확히 같은 값을 내는지는 분할 이벤트가 섞인
멀티 티커 테스트로 `assertEquals`(레코드 전체 비교) 검증했다.

## 결과

전부 실제 운영(`http://134.185.97.175:30081/api/tickers`, 57개 티커) 기준.

| 단계 | 응답 시간(개별 측정값) | 평균 |
|---|---|---|
| 01번 수정 전(배당 건수 N+1) | 7.73s / 9.46s / 16.91s | 11.36s |
| 01번 수정 후(안정화 상태) | 0.75 / 0.90 / 1.00 / 1.09 / 1.35s | 1.02s |
| **02번 첫 시도(상관 서브쿼리) — 실패** | **41.8s / 44.1s** | **43.0s** |
| 02번 최종(GROUP BY+JOIN), 콜드스타트 직후 | 4.96s | — |
| 02번 최종, 안정화 상태 | 0.76 / 0.83 / 0.90 / 1.39 / 1.45s | 1.07s |

쿼리 수는 코드 구조상 티커당 6개(약 342건 전체)에서 배치 조회 2개 +
가격 조회 1개 + `findAll` 1개 + TTM 내부 티커당 2개(114건)로,
대략 342건 → 118건대로 줄었을 것으로 추정된다 — 다만 이번엔
Hibernate SQL 로그로 직접 세지 못했다(01번 때와 달리 실측 안 됨,
아래 한계에 남김).

**정직하게 밝혀둘 것**: 01번 수정 후(1.02s)와 02번 최종(1.07s)의
안정화 상태 응답시간은 사실상 차이가 없다. 57개 티커 규모에서는
쿼리 개수를 더 줄여도 체감 응답시간에는 거의 안 잡힌다 — 이
크기에서는 JVM/직렬화/기본 오버헤드가 이미 쿼리 비용을 압도하는
바닥에 가까워 보인다. 이번 수정의 가치는 "지금 당장 빨라짐"이
아니라 "티커 수가 늘어나도 쿼리 수가 비례해서 안 늘어나는 구조로
바꿔둠"(확장성)에 더 가깝다.

## 다음/한계

- `TtmDividendAggregationService`의 티커당 2쿼리(약 114건)는 여전히
  남아있다. 4개 화면이 공유하는 컴포넌트라 이번엔 건드리지 않았다 —
  건드리려면 그 4곳의 호출 패턴(서로 다른 날짜 윈도우로 반복 호출)까지
  다시 설계해야 한다.
- 이번 최종 수정은 쿼리 수 감소를 코드 구조로만 추정했고, 01번처럼
  Hibernate SQL 로그로 직접 세어 검증하지 못했다 — 운영 DB 접근이
  이번엔 도구 권한으로 막혔기 때문. 다음에 여유 있을 때 실측으로
  채워 넣을 것.
- 상관 서브쿼리 실패에서 얻은 교훈: 쿼리 정확성은 임베디드 DB로
  테스트할 수 있어도, 쿼리 **성능**은 실제 엔진(MySQL)의 실행 계획을
  보지 않으면 알 수 없다. 다음에 이런 "행마다 재실행되는" 형태의
  쿼리를 짤 땐, 배포 전에 최소 `EXPLAIN`이라도 실제 DB로 확인하는
  단계를 스킵하지 않는다.
