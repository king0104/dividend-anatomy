# 지표 추가 워크플로우

이 프로젝트의 반복 단위는 "지표 하나 추가하기" 하나뿐이다 (기여도 분해,
성장률 둔화, 삭감 이력, 변동성, 이상치 제거 — 전부 같은 모양). 아래 8단계는
남의 템플릿이 아니라 이 프로젝트에서 실제로 작업하며 도출한 순서다.

```
1. /spec   스펙 작성 → docs/specs/{지표명}.md
           계산식 · 기준 시점 · 반올림 방향 · 예외 케이스 명시

2. 예측    AI가 틀릴 지점을 docs/ai-predictions.md 에 먼저 기록

3. /test   스펙 기반 테스트 먼저 작성
           손계산으로 검증한 케이스 최소 2개 포함

4. plan    Plan mode로 구현 계획 요청
           계획을 반드시 한 군데 수정 (고칠 데가 안 보이면 아직 이해 못 한 것)
           AI 판단에 "왜 이렇게 했어?" 캐묻기

5. 구현    acceptEdits 모드로 속도

6. 검증    hooks 자동 실행 (compile + test) + ArchUnit

7. 기록    커밋 메시지 Catch: 줄
           예측표 결과 칸 채우기

8. /clear
```

## 각 단계 참고

- **1단계**: `/spec` 커맨드(`.claude/commands/spec.md`)가 4개 필수 항목을
  빈 칸으로 안 남기게 강제한다.
- **2단계**: 이미 있는 기저 예측(T+2 규칙 착각, 특별배당 합산, `double` 사용,
  분할 단위 불일치, 세율 혼동, Spring Boot 3.x 관성) 외에 이 지표 고유의
  실패 지점이 있는지 확인한다.
- **3단계**: `/verify` 커맨드는 구현 이후 대조용이지, 테스트 작성 자체를
  대체하지 않는다 — 순서상 테스트가 먼저다.
- **4단계**: Plan mode에서 나온 계획을 무비판적으로 승인하지 않는다. 최소
  한 곳은 반드시 고쳐서, AI 계획을 검토 없이 그대로 실행하지 않았다는
  증거를 남긴다.
- **6단계**: `.claude/settings.json`의 Hooks(`PostToolUse` → compileJava,
  `Stop` → test)가 자동으로 돌지만, ArchUnit처럼 "검사 규칙 자체가 제대로
  작동하는가"는 별도로 의심해야 한다 (`docs/ai-defects/01-...` 사례 참고).
- **7단계**: 실패를 실시간으로 기록하지 못했으면 `/defect`로 지금이라도
  기록한다. 몰아서 쓰면 기억이 흐려진다.
- **8단계**: 컨텍스트가 길어지면 판단력이 떨어진다. 기능 하나가 끝나면
  `/clear`.
