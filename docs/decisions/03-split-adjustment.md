# 03. 가격은 분할 조정, 배당은 raw — 단위 불일치 실제 확인

**날짜**: 2026-08-23

## 왜 확인했나

`docs/ai-predictions.md` #4는 "주식 분할 전후 배당금 단위 불일치를 무시할
것"이라는 예측이었다. 가격·배당 영속성 엔티티를 설계하기 전에, 이게
실제로 일어나는 문제인지 두 제공자(Massive, Twelve Data)의 실제 응답으로
확인했다.

## 확인 방법과 결과

### Massive 배당 데이터 — KO 2012-08-13 2:1 분할 전후

```
curl "https://api.massive.com/v3/reference/dividends?ticker=KO&limit=1000&apiKey=..."
```

| ex_dividend_date | cash_amount |
|---|---|
| 2012-03-13 | 0.51 |
| 2012-06-13 | 0.51 |
| **2012-08-13 (2:1 분할)** | |
| 2012-09-12 | 0.255 |
| 2012-11-28 | 0.255 |

분할 직후 배당이 **정확히 절반**(`0.51 → 0.255`)이다. 만약 데이터가
분할 조정(소급 반영)되어 있었다면 2012-03-13, 2012-06-13 값도 이미
`0.255`로 나왔어야 한다. 그렇지 않다는 건 **Massive의 배당 금액은 raw —
"그 배당을 지급한 시점의 주식 수" 기준 그대로**라는 뜻이다.

### Twelve Data 가격 시계열 — NVDA 2024-06-10 10:1 분할 전후

```
curl "https://api.twelvedata.com/time_series?symbol=NVDA&interval=1day&start_date=2024-06-05&end_date=2024-06-14&apikey=..."
```

| date | close |
|---|---|
| 2024-06-05 | 122.44 |
| 2024-06-06 | 120.99 |
| 2024-06-07 | 120.88 |
| **2024-06-10 (10:1 분할)** | |
| 2024-06-11 | 120.91 |
| 2024-06-12 | 125.20 |
| 2024-06-13 | 129.61 |

분할 전후로 가격이 **연속적**이다 ($120대). 분할 전 실제 거래가는
$1200대였는데 그렇게 나오지 않았다는 건 **Twelve Data의 종가는 이미
split-adjusted — "지금(가장 최근) 주식 수" 기준으로 과거까지 역산돼
있다**는 뜻이다 (일반적인 주가 시계열 API 관행).

## 결론

**가격은 "지금 주식 수" 기준, 배당은 "그 당시 주식 수" 기준으로 서로 다른
단위다.** 분할 경계를 걸친 TTM 배당 합계를 가격과 그냥 나누면(조정 없이)
분할 이전 구간의 배당이 실제보다 과대평가된다 — 예를 들어 KO가 2012년에
분할 안 했다고 가정하고 2012-06-13 배당(`0.51`)을 지금 주식 수 기준
가격과 나누면, 실제로는 지금 주식 1주가 그 당시 반 주에 해당하므로 배당도
반으로 나눠야 맞다(`0.255`)는 걸 놓치게 된다.

## 결정 — 엔티티 설계에 반영

- `DividendPayment.amount`는 **raw 그대로 저장** (원본 사실을 훼손하지
  않는다 — 나중에 다시 계산해야 할 수도 있고, raw 값 자체가 감사
  가능해야 한다).
- 분할 이력은 별도 `SplitEvent` 엔티티로 저장 (Massive
  `/v3/reference/splits`의 `split_from`/`split_to`를 그대로 `ratio =
  split_to/split_from`로 변환).
- **분할 조정 계산(raw 배당 ÷ 그 이후 발생한 분할 비율의 누적곱)은 이번
  엔티티 설계에는 포함하지 않고, TTM 집계 서비스(다음 증분)에서
  `SplitEventRepository`를 조회해 계산한다** — 원본 데이터를 변형하지
  않고, 계산 시점에 조정하는 방식을 택했다. 이유: raw 사실과 계산된
  값을 분리해두면, 나중에 분할 조정 로직 자체에 버그가 있었다는 게
  밝혀져도 원본을 다시 조회할 필요 없이 재계산만 하면 된다.

## 단순화 가정 (TtmDividendAggregationService 구현, 2026-08-23)

배당 조정 로직을 실제로 구현하면서(`TtmDividendAggregationService.
splitAdjustedAmount()`), "그 배당 이후 발생한 분할"의 상한을 어디까지로
볼지 정해야 했다. 원칙적으로는 "가격 데이터를 마지막으로 가져온 시점"
기준이어야 정확하다 — Twelve Data 시계열이 그 시점 기준으로 역산돼
있으므로. 하지만 이 프로젝트는 아직 배치 수집 어댑터가 없어서 "가격을
마지막으로 가져온 시점"이라는 개념 자체가 DB에 안 남는다.

**단순화**: `SplitEventRepository.findByTickerAndExecutionDateAfterOrderByExecutionDateAsc()`
로 상한 없이 "그 배당 이후 발생한 모든 분할"을 다 가져와서 누적곱으로
나눈다. 즉 항상 "지금 알고 있는 가장 최신 분할 이력" 기준으로 조정한다.

**이게 틀릴 수 있는 경우**: 가격을 오래전에 가져온 뒤로 분할이 하나 더
생겼는데 가격을 다시 안 가져왔다면, 저장된 가격은 옛 분할 기준인데
배당은 새 분할까지 반영해서 조정되어 단위가 다시 어긋난다. 배치 수집
어댑터를 만들 때 "가격을 새로 가져올 때마다 분할 이력도 같이 갱신한다"는
불변식을 지켜야 이 가정이 유효하다 — 어댑터 설계 시 반드시 지킬 것.

## 남은 것

- Twelve Data 가격이 "가장 최근 조회 시점" 기준으로 역산되는지, 아니면
  각 요청마다 "그 요청 시점"을 기준으로 역산되는지는 확인 안 함 —
  일반적인 API 관행상 후자는 드물지만, 배치 수집 어댑터를 만들 때
  실제로 재확인 필요.
- 위 "단순화 가정"이 배치 수집 어댑터 설계 시점에 실제로 지켜지는지
  재확인 필요.
