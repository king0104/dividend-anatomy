# "프리프롬프팅" 프레임워크와 이 프로젝트의 대응 관계

## 출처

우아콘 2025, 임동준(우아한형제들), "어제 쓴 프롬프트 오늘도 그대로
쓰시나요?" — Anthropic 공식 프롬프트 엔지니어링 가이드의 "프롬프트
엔지니어링 이전에" 절과 켄트 벡의 팟캐스트 인터뷰(불변 테스트, "올바른
문제를 정의하고 의도를 설계해서 입력하는 것"이 AI 시대에 가치가
1000배가 된 10%)를 근거로, 프롬프팅 전에 거쳐야 할 단계를
"프리프롬프팅"이라 이름 붙이고 세 단계로 정리했다.

1. **성공 기준의 명확한 정의** — 모호하게 "잘 되면 좋겠다"가 아니라
   측정 가능한 기준을 먼저 텍스트로 쓴다.
2. **경험적으로 반복 검증할 방법** — 한 번 되고 안 되고가 아니라,
   여러 샘플로 통계적으로 확인할 수 있는 환경을 만든다.
3. **개선하고자 하는 초안(프롬프트)** — 첫 시도부터 완벽을 기대하지
   않고, 버전을 올려가며 의도에 가까워지는 과정으로 설계한다.

여기에 켄트 벡의 "불변 테스트"(LLM이 테스트 자체는 못 건드리게 고정 —
테스트가 곧 나의 의도이므로)와 "복잡한 문제를 작게 쪼갠다", "프롬프트를
코드처럼 버전 관리·리뷰·자산화한다"는 원칙이 더해진다.

## 이 프로젝트가 이미 대응하고 있던 것

이 프레임워크를 알기 전부터, 이 프로젝트(CLAUDE.md, `docs/workflow.md`)는
사실상 같은 개념을 이미 나름의 형태로 쓰고 있었다.

| 프리프롬프팅 요소 | 이 프로젝트의 대응 장치 |
|---|---|
| 1. 성공 기준의 명확한 정의 | `/spec` 커맨드 — 계산식·기준시점·반올림 방향·예외 케이스 4가지를 빈 칸으로 못 남기게 강제 (`docs/specs/*.md`) |
| 1-보조. 실패 케이스도 먼저 정의 | `docs/ai-predictions.md` — 구현 전 "AI가 이걸 틀릴 것이다"를 미리 적어두고 나중에 적중 여부 채움 |
| 2. 경험적·반복적으로 검증할 방법 | 손계산 테스트 케이스 + `./gradlew test`(전체 스위트) + `/verify` 커맨드(계산 결과를 손계산과 대조) |
| 2-보조(신규). 실데이터로도 검증 | 오늘 `docs/workflow.md` 7단계로 새로 추가 — 아래 "오늘 새로 반영한 것" 참고 |
| 3. 개선하고자 하는 초안(버전 관리하며 개선) | Plan Mode(구현 전 계획을 사람이 검토, 최소 1곳 수정) + 커밋의 `Plan:`/`Catch:` 줄로 "무슨 의도로 시작해서 뭐가 안 맞았는지"를 기록 |
| 복잡한 문제를 작게 쪼갠다 | "지표 하나 추가하기"가 반복 단위. 그 안에서도 순수 계산 로직 → DB 연결 서비스 → REST 컨트롤러로 항상 증분을 쪼갬(배당수익률 기여도 분해, 삭감 이력 탐지 둘 다 이 순서로 진행) |
| 프롬프트/의도의 자산화 | `docs/specs/`, `docs/decisions/`, `docs/ai-predictions.md`, `docs/ai-defects/` — 프롬프트 원문 대신 "왜 이렇게 결정했는지/뭐가 틀렸는지"를 구조화된 문서로 축적 |
| 켄트 벡의 "불변 테스트" | 부분적으로만 대응 — 손계산 테스트 케이스와 방어적 불변식(`TtmDividendSummary` 생성자 검증)이 비슷한 역할을 하지만, 아래 "갭" 참고 |

## 오늘 새로 반영한 것 — 7단계 "실데이터 검증"

삭감 이력 탐지 지표를 구현하며 정확히 이 프레임워크가 경고하는 상황을
직접 겪었다: 손으로 만든 테스트 59개가 전부 통과한 상태에서 실제 KO
데이터로 API를 호출하니 `foundCount(5) > expectedCount(4)` 예외가
났다(`docs/ai-defects/07`). 1차 수정 후에도 재검증하지 않았다면
"통과했으니 끝"으로 착각하고 넘어갔을 것 — 진짜 원인(실제 배당
캘린더가 91.25일 간격이 아니라 77~102일로 불규칙함)은 22년치 KO
데이터 전체를 스크립트로 훑어야만 드러났다.

이건 "경험적으로 반복 검증할 방법"이 **테스트 스위트 하나로는
불충분할 수 있다**는 프레임워크의 문제의식과 정확히 같은 지점이다 —
그래서 `docs/workflow.md` 8단계 워크플로우에 **7단계: 실데이터
검증**(테스트 통과 후 서버를 실제로 띄워 손으로 안 만든 진짜 데이터로
최소 1회 확인)을 새로 추가했다.

## 아직 안 된 것 (갭)

- **구조적으로 "불변 테스트"가 아니다.** 켄트 벡의 핵심은 "LLM이 테스트
  자체를 못 건드리게 잠근다"인데, 이 프로젝트는 스펙·테스트·구현을
  전부 AI(나)가 쓴다. 지금은 사용자가 Plan Mode 단계에서 계획을
  검토하고 스펙 갈림길에서 직접 답을 정하는 것으로 그 역할을 대신하고
  있지만, 테스트 파일 자체를 사람이 먼저 쓰고 AI는 그걸 통과시키는
  코드만 짜게 하는 형태는 아니다. 더 강하게 가려면 핵심 계산 로직의
  테스트만이라도 사용자가 먼저 작성하거나, 최소한 구현 전에 테스트
  내용을 리뷰·승인하는 단계를 넣는 걸 고려할 수 있다.
- **프롬프트 리뷰 문화가 없다.** 발표에서 강조한 "코드 리뷰 대신
  프롬프트 리뷰"는 이 프로젝트엔 없음 — 프롬프트 자체가 아니라
  스펙/계획 문서를 리뷰하는 형태로 대체돼 있다.
  "가급적 해당 작업 맥락을 최소한으로 아는 사람한테 프롬프트를
  보여주고 이해되는지 확인한다"는 골든룰도 적용한 적 없다.
- **프롬프트를 버전 파일(`prompts/v1.md`, `v2.md`)로 관리하지 않는다.**
  대신 커밋 메시지의 `Plan:`/`Catch:` 줄과 `docs/decisions/`가 그
  역할을 겹쳐서 하고 있다 — 목적(왜 이렇게 했는지 나중에 되짚기)은
  같지만 형태는 다르다.

## 결론

새로운 방법론을 도입한 게 아니라, 이미 하고 있던 것(스펙 우선, 사전
예측, Plan Mode 검토, 결정 문서화)이 이 프레임워크의 1·3단계와
거의 그대로 겹친다는 걸 확인했고, 이 프레임워크가 강조하는 2단계
("경험적 반복 검증")의 허점 — 테스트 스위트를 통과했다고 검증이 끝난
게 아니라는 것 — 을 오늘 실제로 겪고서 워크플로우에 명시적으로
추가했다. 구조적 "불변 테스트"와 "프롬프트 리뷰/자산화"는 아직
갭으로 남아있고, 향후 검토 대상이다.
