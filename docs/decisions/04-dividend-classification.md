# 04. 정기/특별배당 분류와 지급 횟수는 Massive가 이미 제공 — 직접 추론 안 함

**날짜**: 2026-08-23

## 왜 재검토했나

CLAUDE.md와 `docs/specs/yield-change-decomposition.md` 0절은 "정기/특별
배당 분류"와 "연간 정기 배당 지급 횟수(`regularPaymentsPerYear`)"를
지급 이력에서 **직접 추론해야 하는 알고리즘**으로 가정했다 — Day 1
예측표에도 "구분 로직이 자명하지 않음"(#2)이라고 적어뒀다. 실제로
배당 수집 어댑터를 만들기 직전에 Massive 배당 응답을 다시 자세히
보니 `dividend_type`, `frequency` 필드가 있길래, 이게 실제로 이 문제를
풀어주는지 COST(코스트코)로 검증했다.

## 확인 방법과 결과

COST는 2023-12-27에 주당 $15짜리 특별배당을 지급한 게 잘 알려져 있다
(정기 배당은 그 시점 분기당 $1.02 수준). Massive 응답:

```
2024-02-01  1.02  CD  4
2023-12-27  15    SC  0    ← 알려진 특별배당
2023-11-02  1.02  CD  4
2023-08-24  1.02  CD  4
```

- **정기 배당**: `dividend_type=CD`(Cash Dividend), `frequency=4`
- **특별배당**: `dividend_type=SC`(Special Cash), `frequency=0`

금액(1.02 vs 15)만 봐도 명백하지만, 필드 자체가 이미 구분해서 내려준다는
게 핵심 확인 사항이다 — 우리가 "이 금액이 패턴에서 벗어나니 특별배당일
것이다" 같은 휴리스틱을 만들 필요가 없다.

## 결정

- **`dividend_type` → `DividendType`**: `CD`는 `REGULAR`, `SC`는
  `SPECIAL`로 매핑한다. 그 외 코드(`LT`, `ST`, `CG` 등 — polygon.io
  계열 API의 일반적인 배당 유형 코드, REIT/펀드성 종목에서 나올 수
  있음)를 만나면 **조용히 REGULAR로 넘기지 않고** 예외를 던지거나
  로그를 남겨 사람이 확인하게 한다 (CLAUDE.md "데이터 불완전 시 조용히
  넘어가지 않는다" 원칙).
- **`frequency` → `Ticker.regularPaymentsPerYear`**: 배당 수집 시 응답의
  `frequency` 값을 그대로 `Ticker.regularPaymentsPerYear`에 반영한다.
  더 이상 "수동으로 채워 넣어야 하는 값"이 아니다.
- **직접 추론 알고리즘("지급 이력에서 정기 주기를 추론")은 만들지
  않는다.** Massive가 제공하는 분류를 신뢰하는 쪽을 택했다 — 이유:
  (1) 실제로 알려진 특별배당 사례로 검증됐고, (2) 자체 추론 로직을
  만들면 그 자체가 새로운 버그 표면적이 되는데, 이미 검증된 제공자
  데이터를 안 쓰고 굳이 재발명할 이유가 없다.

## 남은 위험

- `frequency=0`이 "특별배당이라 주기 없음"인지 "아직 주기가 안 잡힌
  신규 배당"인지 구분이 안 될 수 있다 — 실제 배치 수집에서 이런 케이스가
  나오면 그때 재검토.
- Massive의 분류 자체가 틀릴 가능성(제공자 데이터 오류)은 여전히 있다 —
  다만 이건 "우리가 추론 로직을 만들어도" 마찬가지로 안고 가야 할
  위험이라, 이 결정으로 새로 생기는 위험은 아니다.
- `CD`/`SC` 외 코드가 실제로 이 프로젝트가 다루는 배당킹/우량주
  유니버스에서 나오는지는 좀 더 종목을 확인해봐야 한다 — 지금은 COST
  하나만 확인.
