# 08. 배포 — 기존 개인 k3s 클러스터에 신규 워크로드로

**날짜**: 2026-08-24

## 왜 확인했나

PROJECT.md 마지막 남은 항목(배포)을 진행하려면 실행 환경이 필요하다.
새 OCI 컴퓨트 인스턴스를 띄울지, 사용자가 예전에 만들어둔 개인 k3s
클러스터를 쓸지부터 확인했다 — 근거 없이 새 인스턴스를 만들면 무료
티어를 낭비하거나(이미 다 썼을 수도 있음), 다른 목적으로 준비해둔
클러스터를 놔두고 중복 인프라를 만드는 셈이 된다.

## 확인 방법과 결과

- `oci limits resource-availability get`으로 실제 남은 할당량 확인 —
  Always Free `VM.Standard.A1.Flex`(Ampere ARM64) 4 OCPU/24GB 전체가
  기존 개인 k3s 3대(master 2 OCPU/12GB + worker 1 OCPU/6GB × 2)로
  이미 꽉 차 있음. `VM.Standard.E2.1.Micro` 무료 풀은 별도로 안 쓰고
  있었지만(0/2), 사용자가 기존 클러스터의 여유 용량을 쓰는 쪽을
  선택.
- 기존 클러스터 워크로드 확인(`kubectl get pods -A`) — `nginx-test`
  하나 + Prometheus/Grafana 모니터링 스택뿐, 새 워크로드를 얹을 여유
  충분.
- `oci network subnet get` / `security-list get`으로 k3s 노드
  VCN(`vcn-20260226`, 10.0.0.0/16)과 dividend-anatomy MySQL의 VCN이
  **같다**는 걸 확인. MySQL 보안 목록에 이미 "10.0.0.0/16 전체"에
  3306을 열어둔 규칙(`dividend-anatomy MySQL (VCN 내부만)`)이 있어서,
  클러스터에서 DB로 직접 접속 가능 — Bastion 터널이 전혀 필요 없다.
  배포 후 pod 로그에서 HikariCP가 `10.0.2.201:3306`에 바로 연결
  성공한 걸로 실제 확인.
- 로컬 개발 머신(Apple Silicon)과 클러스터 노드(Ampere ARM64)가 둘 다
  arm64라 크로스 컴파일 없이 네이티브 이미지 빌드 가능.
- 클러스터에 ingress controller/LoadBalancer가 없고, 기존
  `nginx-test`도 `NodePort`(30080, 0.0.0.0/0에 공개)로 노출 중임을
  확인 — 이 프로젝트만 별도로 TLS·ingress를 새로 도입하지 않고 같은
  패턴을 따르기로 함.

## 결정

- **새 인스턴스를 만들지 않고 기존 개인 k3s 클러스터에 새 워크로드로
  배포한다.**
- **컨테이너 레지스트리를 새로 만들지 않는다.** 로컬에서
  `docker build --platform linux/arm64` → `docker save` → 3개 노드에
  `scp` → 각 노드에서 `k3s ctr images import`로 사이드로드하고,
  Deployment에 `imagePullPolicy: Never`를 명시한다. 코드가 바뀌면
  이 과정을 수동으로 반복해야 하지만(자동 CI/CD 없음), 단발성
  포트폴리오 배포 범위에서는 레지스트리 인프라를 새로 도입하는 것보다
  낫다고 판단.
- **`NodePort`(30081, HTTP 평문)로 노출한다.** 기존 클러스터의 확립된
  패턴(`nginx-test`의 30080)과 동일 수준 — TLS는 의도적으로 범위 밖.
- **OCI 보안 목록은 추가만 한다.** 기존 규칙(SSH 22, ICMP, 기존
  NodePort 30080, k3s API 6443, MySQL 3306)을 그대로 두고 30081 규칙만
  덧붙인다.

## 배포 중 발견한 문제 — 클러스터 크로스노드 네트워킹이 원래부터 깨져 있었음

보안 목록에 30081을 열었는데도 `master`와 두 워커 중 하나의 공인
IP로는 계속 응답이 없었다. 원인을 파고드니 **이 클러스터는 애초에
서로 다른 노드에 있는 pod끼리 통신이 안 되는 상태였다** — 새로 생긴
버그가 아니라, 이미 떠 있던 `nginx-test`도 자기가 뜬 노드(`master`)
IP로만 응답하고 다른 두 노드 IP로는 똑같이 안 되는 걸 재현해서 확인
(176일간 아무도 다른 노드 IP로 접속을 안 해봐서 발견이 안 됐을
뿐이었다).

처음엔 `nodeSelector`로 pod를 한 노드에 고정하는 우회로 넘어갔지만,
그러면 사실상 "3대짜리 클러스터"가 아니라 "노드 하나에 묶인 서버"와
다를 게 없어서(레플리카 분산도, 노드 장애 시 자동 복구도 안 됨) 근본
원인을 끝까지 팠다. 실제로는 **레이어가 다른 문제 4개가 겹쳐 있었다**:

1. **OCI 보안 목록에 UDP 8472(flannel VXLAN이 쓰는 포트) 규칙이 아예
   없었음** — 열려 있던 건 전부 TCP/ICMP뿐. 추가로 열었다.
2. VXLAN 자체에 체크섬 문제가 있다고 의심해서(`tcpdump`엔 패킷이
   도착하는데 `/proc/net/snmp`의 UDP 수신 카운터는 그대로) flannel
   백엔드를 `host-gw`(캡슐화 없는 순수 라우팅)로 바꿔봤지만, OCI의
   "private IP로 라우팅" 기능이 **같은 서브넷 안에서는 공식적으로
   지원되는 패턴이 아니어서**(웹 검색으로 확인 — 공식적으론 서로
   다른 서브넷 사이 라우팅용) 이 경로는 막다른 길이었다. VXLAN으로
   되돌림.
3. **진짜 원인**: `iptables -L INPUT -n` (인터페이스 정보 없이) 로는
   "무조건 허용"처럼 보였던 규칙이, `-v` 옵션으로 다시 보니 실제로는
   `in=lo`(루프백 전용) 조건이 걸려 있었다 — 즉 **호스트 방화벽이
   실제 네트워크로 들어오는 트래픽 중 명시적으로 안 열어준 포트는
   전부 막고 있었다.** SSH(22)·기존 NodePort(30080)처럼 수동으로 연
   포트, 그리고 k8s가 스스로 관리하는 NodePort 규칙만 통과했을 뿐,
   VXLAN이 쓰는 UDP 8472는 **OCI 보안 목록만 열고 호스트
   iptables는 한 번도 안 열었던 것**이 진짜 원인이었다. 순수
   VXLAN·k8s와 무관한 일반 UDP 패킷으로(파이썬 소켓 스크립트) 직접
   검증해서 확인 — TCP는 되는데 UDP만 막혀 있었다.
4. `iptables` FORWARD 체인에도 부수적으로 발견한 문제가 있었다 —
   pod CIDR을 허용하는 `FLANNEL-FWD` 체인 점프가 무조건 REJECT
   규칙 **뒤에** 있어서 죽어 있었다(host-gw 시도 중 발견, 순서
   교정 — vxlan으로는 원래 안 쓰이는 경로라 지금까진 안 드러났을
   뿐).

**수정**: 3개 노드 전부에 `iptables -I INPUT -p udp --dport 8472 -j
ACCEPT` 추가 후 `netfilter-persistent save`로 재부팅에도 남게
저장. `nodeSelector` 제거, 레플리카를 3개로 늘려 노드 3대에 하나씩
흩어지게 만든 뒤 세 노드 공인 IP 전부로 접속해서 실제로 크로스노드가
되는지 확인(pod가 `master`에 떠 있어도 `worker-1` IP로 접속해서
정상 응답 확인) — 검증 후 원래 레플리카 수(1개)로 되돌림. host-gw
실험 중 추가했던 VCN 라우트 테이블 규칙과 `skip-source-dest-check`는
더 이상 필요 없어서 원상복구.

## 남은 위험

- 이미지 사이드로드 방식이라 코드가 바뀔 때마다 3개 노드에 수동으로
  다시 배포해야 한다 — 자동화된 CI/CD 파이프라인은 이 프로젝트
  범위에서 의도적으로 도입하지 않음.
- TLS 없음 — 데모/포트폴리오 목적의 알려진 제약이며, README와
  progress-log에도 명시했다.
- 호스트 iptables 규칙은 이 클러스터에서 계속 수동 관리 방식이다
  (`netfilter-persistent`로 저장은 했지만, ufw 같은 선언적 도구는
  없음) — 다음에 새 포트를 열 때도 OCI 보안 목록과 호스트
  iptables **둘 다** 잊지 말고 같이 열어야 한다는 게 이번에 얻은
  교훈이다.
